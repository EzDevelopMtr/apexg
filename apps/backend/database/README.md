# Base de datos — APEX GYM

Esta carpeta contiene la capa inicial de base de datos del backend:

- **modelo lógico** en DBML (`schema.dbml`),
- **migración inicial** de PostgreSQL (`migrations/001_initial_schema.sql`),
- **datos globales** independientes de empresa (`migrations/002_seed_modules_permissions.sql`),
- **seeds por empresa** que se aplican con un `company_id` concreto (`seeds/company/*`).

Todos los scripts SQL son para PostgreSQL y hoy están pensados para ejecutarse con `psql`.
Aún **no** hay conexión desde NestJS, ORM ni automatización de migraciones (ver [Pendiente](#pendiente)).

## Modelo lógico

`schema.dbml` es la referencia del modelo y puede visualizarse en herramientas compatibles con DBML
(p. ej. [dbdiagram.io](https://dbdiagram.io)). Actualmente define **27 tablas**, agrupadas en estas áreas:

- **Plataforma / empresas** — `platform_admins`, `companies`.
- **Usuarios, roles y permisos** — `users`, `roles`, `modules`, `permissions`, `role_permissions`.
- **Clientes** — `clients`, `client_notes`.
- **Membresías** — `membership_types`, `client_memberships`.
- **Pagos** — `payments` (una sola tabla para pago completo y abonos).
- **Entrenadores** — `trainers`, `trainer_commissions`.
- **Promociones** — `promotion_groups`, `promotion_group_members`.
- **Egresos** — `expense_categories`, `expenses`.
- **Inventario** — `inventory_items`, `inventory_movements`, `equipment_maintenance`.
- **Operación diaria** — `daily_logs`, `monthly_closures`.
- **Asistencia** — `attendances`, `client_biometrics`.
- **Auditoría y notificaciones** — `audit_logs`, `notifications`.

El detalle completo de columnas está en `schema.dbml`; este README no lo reproduce.

## Migración inicial — `001_initial_schema.sql`

- Crea las **27 tablas** con sus PK, FK, restricciones `UNIQUE` e índices.
- Habilita la extensión `pgcrypto` (`CREATE EXTENSION IF NOT EXISTS pgcrypto`).
- Los IDs de las entidades de negocio son `UUID … DEFAULT gen_random_uuid()`.
- `roles`, `modules` y `permissions` usan `INTEGER GENERATED BY DEFAULT AS IDENTITY`.
- **No** contiene datos de negocio.
- **No** contiene triggers, stored procedures, funciones, vistas, RLS/políticas ni tipos `ENUM`.
- Toda la migración va dentro de `BEGIN; … COMMIT;`.
- Está pensada para ejecutarse sobre una base PostgreSQL **vacía**.

```bash
psql "$DATABASE_URL" \
  -f apps/backend/database/migrations/001_initial_schema.sql
```

## Datos globales — `002_seed_modules_permissions.sql`

Carga datos **independientes de `company_id`**:

- **11 módulos** (`Usuarios`, `Clientes`, `Membresias`, `Pagos`, `Entrenadores`, `Egresos`,
  `Inventario`, `Finanzas`, `Apartado diario`, `Asistencia`, `Auditoria`).
- **37 permisos**, con `code` del tipo `modulo.accion` (p. ej. `clientes.create`) y `action` en
  `create | read | update | delete | export`.

Es **idempotente**: `modules` usa `ON CONFLICT (name)` y `permissions` usa `ON CONFLICT (code)`.
`module_id` se resuelve por `modules.name`, sin IDs fijos.

Debe ejecutarse **después** de `001_initial_schema.sql`:

```bash
psql "$DATABASE_URL" \
  -f apps/backend/database/migrations/002_seed_modules_permissions.sql
```

## Datos por empresa — `seeds/company/`

`roles`, `role_permissions`, `membership_types` y `expense_categories` **no son globales**: cada
empresa tiene sus propios registros, ligados por `company_id`. Por eso estos seeds viven en
`seeds/company/` y **exigen** un `company_id`.

### `company_id`

Los seeds por empresa reciben una variable de `psql` llamada `company_id`:

```bash
psql "$DATABASE_URL" \
  -v company_id='UUID-DE-LA-EMPRESA' \
  -f apps/backend/database/seeds/company/001_roles_permissions.sql
```

Dentro del SQL:

- `:'company_id'::uuid` — expande la variable a un literal entrecomillado y lo castea a `uuid`.
- `\set ON_ERROR_STOP on` — detiene la ejecución ante el primer error (evita commits parciales).

Si el `company_id` no corresponde a una fila de `companies`, la FK
(`roles.company_id` / `membership_types.company_id` / `expense_categories.company_id` → `companies.id`)
falla y la transacción hace `ROLLBACK`.

Estos scripts están diseñados específicamente para `psql` (por `\set` y `:'company_id'`). No es un
error: es la forma de ejecución actual mientras no exista automatización desde el backend.

## Inicialización de una base nueva

Orden completo:

1. Ejecutar `001_initial_schema.sql`.
2. Ejecutar `002_seed_modules_permissions.sql`.
3. Crear la empresa en `companies`.
4. Obtener su `companies.id`.
5. Ejecutar, con ese id, los tres seeds de `seeds/company/`.

```bash
# 1. Estructura
psql "$DATABASE_URL" \
  -f apps/backend/database/migrations/001_initial_schema.sql

# 2. Catálogo global (módulos + permisos)
psql "$DATABASE_URL" \
  -f apps/backend/database/migrations/002_seed_modules_permissions.sql

# 3-4. Crear la empresa y capturar su id (ejemplo)
COMPANY_ID=$(psql "$DATABASE_URL" -tAc \
  "INSERT INTO companies (name, currency) VALUES ('Mi Gimnasio', 'COP') RETURNING id")

# 5. Configuración inicial de esa empresa
psql "$DATABASE_URL" \
  -v company_id="$COMPANY_ID" \
  -f apps/backend/database/seeds/company/001_roles_permissions.sql

psql "$DATABASE_URL" \
  -v company_id="$COMPANY_ID" \
  -f apps/backend/database/seeds/company/002_membership_types.sql

psql "$DATABASE_URL" \
  -v company_id="$COMPANY_ID" \
  -f apps/backend/database/seeds/company/003_expense_categories.sql
```

Todavía **no** existe un script único que ejecute todo el proceso; se hace paso a paso.

## Roles

Los crea `seeds/company/001_roles_permissions.sql` para la empresa indicada:

- **Administrador** — recibe **todos** los permisos globales existentes en `permissions`
  (hoy 37). Se resuelve tomando el catálogo completo, no una lista fija.
- **Recepcionista** — recibe **12 permisos** operativos:

  | | | | |
  |---|---|---|---|
  | `clientes.create` | `clientes.read` | `clientes.update` | `membresias.read` |
  | `pagos.create` | `pagos.read` | `entrenadores.read` | `apartado_diario.create` |
  | `apartado_diario.read` | `apartado_diario.update` | `asistencia.create` | `asistencia.read` |

`entrenadores.read` está incluido para que Recepcionista pueda **seleccionar un entrenador** al
registrar planes `Personalizado` / `Semipersonalizado`. Esto **no** implica que el backend deba
exponer `salary` u otra información administrativa del entrenador a Recepcionista: el endpoint del
selector debe devolver solo lo necesario (`id`, `full_name`, `state`, y `max_clients` si se usa para
disponibilidad).

El seed usa `ON CONFLICT` y `granted_at` se omite en el `INSERT` para que tome su `DEFAULT NOW()`.

## Membresías

`seeds/company/002_membership_types.sql` carga 9 tipos:

| Nombre | Precio | Permite abono | Promocional |
|---|---:|:---:|:---:|
| Mensualidad (lunes a sábado) | 65 000 | Sí | No |
| Mes 3 veces por semana | 50 000 | Sí | No |
| Quincena | 45 000 | No | No |
| Semana | 25 000 | No | No |
| Día | 6 000 | No | No |
| Promo amigos/familiar | 60 000 | No | Sí |
| Promo folleto físico | 55 000 | No | Sí |
| Personalizado | 200 000 | Sí | No |
| Semipersonalizado | 150 000 | Sí | No |

- Los planes que **no** permiten abono tienen `minimum_payment = NULL` (no se iguala al precio); el
  "pago completo" se deriva de `allows_partial_payment = FALSE`.
- **Distribución entrenador / negocio** (columnas `trainer_share` / `business_share`):
  - `Personalizado` → 100 000 entrenador / 100 000 negocio.
  - `Semipersonalizado` → 75 000 entrenador / 75 000 negocio.
  - En el resto de planes ambas quedan `NULL`.
- `Personalizado` y `Semipersonalizado` usan `duration_value = 1`, `duration_unit = 'month'` como
  **decisión actual de implementación** (el ERS no fija la duración de esas filas).
- Las reglas de `Promo amigos/familiar` (mín. 3 clientes, pago conjunto el mismo día, permanencia del
  grupo) y de `Promo folleto físico` (cliente nuevo, primer mes, folleto) se validarán en el backend
  con `promotion_groups` / `promotion_group_members`; este seed **no** las implementa.

## Convenciones

- **UUID** para las entidades principales de negocio; **integer identity** para
  `roles` / `modules` / `permissions`.
- **`timestamptz`** para instantes del sistema (`created_at`, `paid_at`, `check_in`, …).
- **`date`** para fechas de negocio sin hora (`birth_date`, `start_date`, `expense_date`, …).
- **`state integer`** para estados simples (el significado de cada valor está comentado en
  `schema.dbml` y en los seeds).
- **`numeric(12,2)`** para dinero; `numeric(12,3)` para cantidades de inventario.
- Datos de negocio separados por **`company_id`** (aislamiento lógico por empresa; la verificación
  de tenant se hará en el backend, no con FK compuestas ni RLS).
- La columna se llama **`password`** pero el backend almacenará ahí el **hash**; la base no aplica
  hashing.
- **Reglas de negocio complejas** (abonos mínimos, disponibilidad de entrenadores, estados,
  promociones) se validan en **NestJS**, no con triggers ni `CHECK`.
- **No** hay tablas de balances financieros: los totales diarios/mensuales se **calculan** desde
  `payments` (ingresos) y `expenses` (egresos).

## Migraciones vs seeds

- **`migrations/`** — estructura y datos globales que la aplicación necesita siempre
  (esquema + módulos + permisos). Se ejecuta una vez por base de datos.
- **`seeds/company/`** — configuración inicial que debe aplicarse **por cada empresa**, con su
  `company_id`.

Nunca ejecutar un seed de `seeds/company/` sin pasar el `company_id` correcto: sin la variable el
script falla, y con un `company_id` equivocado se cargarían datos en la empresa incorrecta.

---

## Idempotencia

Todos los seeds usan `ON CONFLICT` sobre sus claves naturales
(`modules.name`, `permissions.code`, `(company_id, name)`, `(role_id, permission_id)`), por lo que
pueden **reejecutarse** para refrescar los valores base sin crear duplicados.

Los seeds **no** eliminan nada: no hacen `DELETE` ni "sincronizan" quitando configuración que la
aplicación haya añadido después (roles extra, permisos adicionales, nuevas categorías, etc.).
