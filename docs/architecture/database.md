# Arquitectura — Base de datos

Complementa `CLAUDE.md` (reglas) explicando el **porqué** de las decisiones.

## 1. Database-first

El flujo es `SQL → PostgreSQL → introspección → TypeScript`, nunca al revés. Se
eligió porque el equipo escribe SQL con frecuencia (balances, reportes, consultas de
mora por periodos) y quiere control total del DDL. El modelo lógico de referencia es
`apps/backend/database/schema.dbml`; se materializa a mano en migraciones SQL.

## 2. SQL manual como única autoridad de DDL

`apps/backend/database/migrations/*.sql` es lo único que crea o altera estructura.
Se descartó dejar que un ORM administrara el esquema (`synchronize`, `db push`,
`migrate`) para no tener dos definiciones compitiendo y para poder revisar cada
cambio como SQL plano. Una migración aplicada es **inmutable**: los cambios entran
como una nueva migración numerada, nunca editando una anterior. Las migraciones no
son idempotentes (una migración se ejecuta una vez).

## 3. PostgreSQL en Supabase

Supabase se usa **solo** como PostgreSQL 17 administrado (pooler de sesión, puerto
5432, conexión `pg` normal con el rol `postgres`). No se usa su Data API, Auth,
Storage, Realtime ni PostgREST. La Data API está desactivada en el panel; ver
`security.md`.

## 4. Drizzle: ORM runtime + introspección

- **Runtime:** `drizzle-orm/node-postgres` sobre el `pg.Pool`. Da tipado sobre las
  27 tablas sin que el equipo mantenga a mano cientos de interfaces, y permite bajar
  a `sql\`\`` crudo para los reportes complejos.
- **Introspección:** `drizzle-kit pull` (y solo `pull`) regenera
  `src/database/schema/schema.ts` desde la BD ya migrada. `drizzle.config.ts` limita
  a `schemaFilter: ['public']`. La salida temporal (`.drizzle-introspect/`) no se
  versiona.
- `schema.ts` es **derivado**: PostgreSQL es la autoridad. Lleva una cabecera que lo
  documenta y prohíbe usarlo para `generate`/`migrate`.

## 5. Un único `pg.Pool`

`src/database/database.provider.ts` crea **un** `pg.Pool` (desde
`ConfigService.getOrThrow('DATABASE_URL')`) y `drizzle(pool, { schema })` lo
envuelve. `DatabaseModule` (`@Global()`) es el **único** responsable de
`pool.end()` en `OnApplicationShutdown`. `new pg.Pool()` es lazy: no conecta hasta la
primera consulta, por lo que Nest arranca sin BD disponible.

## 6. NUMERIC como string

`pg` devuelve `NUMERIC` como string para no perder precisión. No se registran
parsers globales ni se convierte a `Number`. Los importes monetarios
(`numeric(12,2)`) y las cantidades de inventario (`numeric(12,3)`) viajan como
string entre Drizzle y el dominio; la aritmética monetaria usará una librería
decimal cuando exista lógica de cobros.

## 7. Migraciones 001 / 002 / 003

| Archivo | Qué hace |
|---|---|
| `001_initial_schema.sql` | Crea las 27 tablas, PK, FK, UNIQUE, índices. `pgcrypto`, `gen_random_uuid()`, `INTEGER GENERATED BY DEFAULT AS IDENTITY` para `roles`/`modules`/`permissions`. Sin ENUM, triggers, funciones, vistas ni RLS. |
| `002_seed_modules_permissions.sql` | Catálogo global: 11 módulos + 37 permisos. Idempotente (`ON CONFLICT`). |
| `003_harden_users_auth.sql` | Solo `ALTER TABLE`. `NOT NULL` en las columnas de autenticación de `users` y en las esenciales de `roles`; `state DEFAULT 1`. Reemplaza `users.role_id → roles.id` por la FK compuesta (ver §10). No idempotente. |

## 8. Seeds por empresa

`apps/backend/database/seeds/company/*.sql` (roles+permisos, tipos de membresía,
categorías de egreso) son **herramientas administrativas / referencia**, ejecutables
con `psql -v company_id=...`. Son idempotentes (`ON CONFLICT`). El **producto no
depende de `psql`** para crear una empresa: esa lógica está en el backend (§9).

## 9. `CompanyProvisioningService` — flujo real del producto

`src/provisioning/company-provisioning.service.ts` crea una empresa y toda su
configuración inicial (2 roles, 49 `role_permissions`, 9 membresías, 4 categorías) en
**una sola transacción Drizzle atómica**. No usa los `.sql` en runtime: replica su
especificación. No usa `ON CONFLICT` (un conflicto de UNIQUE debe fallar, no
ocultarse). Sus constantes deben coincidir 1:1 con los seeds SQL — el seed es la
especificación de referencia. `Administrador` recibe **todos** los permisos globales
existentes (dinámico, no una lista de 37 fija).

## 10. FK multiempresa `users` ↔ `roles`

`003` añadió a `roles` la clave candidata `uq_roles_company_role_id UNIQUE (company_id, id)`
(redundante para unicidad — `id` ya es PK — pero necesaria como destino de una FK
compuesta) y a `users` la FK:

```sql
FOREIGN KEY (company_id, role_id) REFERENCES roles (company_id, id)
```

Con `users.company_id` y `users.role_id` ambos `NOT NULL`, esto **garantiza a nivel
PostgreSQL** que el rol de un usuario pertenece a su misma empresa, incluso si alguien
ejecuta SQL manual fuera del backend. La FK directa `users.company_id → companies.id`
se conserva aparte (garantiza que la empresa existe).

## 11. Bug de `drizzle-kit` 0.31.10 con restricciones compuestas

`drizzle-kit pull` 0.31.10 devuelve las columnas referenciadas de una FK/UNIQUE
compuesta **en orden de `attnum` de la tabla destino**, no en el orden del
emparejamiento. Genera:

- `fk_users_company_role` con `foreignColumns: [roles.id, roles.companyId]` (debe ser
  `[roles.companyId, roles.id]`);
- `uq_roles_company_role_id` con `.on(table.id, table.companyId)` (debe ser
  `.on(table.companyId, table.id)`).

Funcionalmente el runtime de `drizzle-orm` no usa estas definiciones (son metadata
para `generate`/`migrate`, que no usamos), pero dejarlas mal convierte `schema.ts` en
documentación engañosa de una restricción de seguridad. **Tras cada `pull` se
corrigen a mano** (con comentario) y se auditan contra `pg_get_constraintdef`. No se
actualiza `drizzle-kit` por ahora; evaluar si una versión posterior lo corrige.
